# 🛡️ Introducción a Branches protegidas y gestión de contribuyentes

En proyectos colaborativos, especialmente en repositorios privados o de equipo, es importante **proteger las ramas críticas** y **controlar quién puede hacer cambios**.
Esto evita errores, sobrescribir trabajo ajeno y garantiza que el flujo de desarrollo sea seguro y organizado.

---

# 🔐 Branches protegidas

Una **branch protegida** (rama protegida) impone reglas sobre cómo se pueden realizar cambios en esa rama.  
Por ejemplo, en una rama principal (`main` o `master`):

- ❌ No se pueden hacer _push_ directos
- ✅ Se deben aprobar **Pull Requests** antes de fusionar
- ✅ Se puede exigir revisión por otro colaborador
- ✅ Se puede requerir que los tests pasen antes de permitir merge

---

# ⚙️ Configurar ramas protegidas en GitHub

1. Ve a tu repositorio en GitHub.
2. Haz clic en **Settings → Branches → Branch protection rules**.
3. Haz clic en **Add rule**.  
4. Escribe el nombre de la rama que quieres proteger (ej.: `main`).
5. Activa las opciones que quieras:
    - **Require pull request reviews before merging** ✅
    - **Require status checks to pass before merging** ✅
    - **Include administrators** (para que los admins también sigan estas reglas) ✅
6. Guarda los cambios.

---

# 👥 Gestión de contribuyentes

Además de proteger ramas, GitHub permite **controlar los permisos de cada colaborador**:

- **Read** → solo ver el repositorio
- **Write** → agregar commits, abrir PR
- **Maintain** → administrar issues, PR y configuración del repo
- **Admin** → control total sobre el repo

> Se recomienda asignar **Write** a desarrolladores que trabajen activamente y **Maintain/Admin** solo a responsables de gestión o mantenimiento.

---

# 🔄 Flujo seguro con ramas protegidas

1. Cada desarrollador crea su propia rama para la funcionalidad o bug que está trabajando:

```bash
git checkout -b feature/nueva-funcionalidad
```

2. Se realizan los commits en esa rama y se hace **push** a GitHub:

```bash
git push origin feature/nueva-funcionalidad
```

3. Se crea un **Pull Request** hacia la rama protegida (`main`).
4. Otro colaborador revisa el PR, aprueba los cambios y se fusiona.

> Esto asegura que la rama principal **nunca reciba cambios sin revisión**, evitando errores y pérdida de trabajo.

---

# ✔️ Resumen rápido

- Las **branches protegidas** evitan cambios directos en ramas críticas.
- Se pueden exigir PRs, revisiones y tests antes de fusionar.
- Los permisos de contribuyentes controlan quién puede modificar el repositorio.
- Combinar ramas personales + PR + ramas protegidas es la forma más segura de trabajar en equipo.
