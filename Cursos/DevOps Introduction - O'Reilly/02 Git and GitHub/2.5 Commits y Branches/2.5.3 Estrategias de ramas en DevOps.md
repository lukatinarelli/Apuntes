# 🌿 Introducción a las ramas en DevOps

Las **ramas (branches)** permiten desarrollar funcionalidades, corregir errores o experimentar sin afectar la rama principal (`main` o `master`).  
En DevOps, una buena estrategia de ramas es **crucial** para mantener un flujo de trabajo organizado y seguro.

---

# 🔀 Tipos de ramas comunes

1. **Main / Master**    
    - Rama principal, siempre estable        
    - Contiene el código listo para producción        
2. **Dev / Development**    
    - Rama de integración de nuevas funcionalidades        
    - Se prueba antes de fusionar con la rama principal        
3. **Feature / Funcionalidad**    
    - Se crea una rama para cada nueva funcionalidad o tarea        
    - Ejemplo:        

```bash
git checkout -b feature/login-social
```

4. **Release / UAT**    
    - Rama para pruebas finales y preparación de lanzamiento        
    - Se crean tags para versiones específicas        
5. **Hotfix / Bugfix**    
    - Para corregir errores críticos directamente en producción        
    - Se fusiona luego a `main` y `dev`        

---

# 🏗️ Flujos de trabajo comunes en DevOps

## 1️⃣ Git Flow

- Ramas bien definidas: `main`, `dev`, `feature`, `release`, `hotfix`    
- Cada tipo de rama tiene un propósito claro    
- Permite un **control total** del ciclo de vida del software    

## 2️⃣ GitHub Flow

- Más simple, ideal para CI/CD    
- Una rama principal (`main`) siempre estable    
- Cada funcionalidad en su **feature branch**    
- Se hace **Pull Request** antes de fusionar    

---

# ⚙️ Buenas prácticas al trabajar con ramas

- Crea ramas **pequeñas y específicas** para cada tarea    
- Haz commits frecuentes y descriptivos    
- Siempre actualiza tu rama antes de fusionar:    

```bash
git pull --rebase origin main
```

- Usa **Pull Requests** para revisión antes de merge    
- Protege la rama `main` con reglas de PR y tests automáticos    

---

# ✔️ Resumen rápido

- Las ramas permiten **desarrollar sin afectar la rama principal**    
- DevOps usa estrategias de ramas para **flujo seguro y controlado**    
- Git Flow → completo y estructurado    
- GitHub Flow → simple, ideal para integración continua    
- Buenas prácticas: ramas pequeñas, commits claros, PRs y protección de ramas
