# ↩️ Revertir cambios en Working Directory

El **Working Directory** (Directorio de Trabajo) es donde realizas tus modificaciones antes de confirmarlas. A veces, experimentas con el código y decides que los cambios no sirven.

En esta etapa, los archivos pueden estar en dos estados:

1. **Modified:** Archivos rastreados (tracked) que han sido editados.
2. **Untracked:** Archivos nuevos que Git aún no vigila.

> [!WARNING]
> **Acción Destructiva:** Revertir cambios en el Working Directory es irreversible. A diferencia de git revert (que crea un nuevo commit), aquí estás borrando trabajo que nunca fue guardado en el historial de Git.

---

# 🛠️ 1. Descartar cambios en archivos modificados

Si has editado un archivo que Git ya conoce, pero quieres volver a como estaba en el último commit (HEAD), tienes dos opciones: el comando moderno y el clásico.

## Opción A: El comando moderno (Recomendado)

Desde la versión 2.23, Git introdujo `git restore` para separar responsabilidades y ser más intuitivo.

```Bash
# Descartar cambios en un archivo específico
git restore archivo.txt

# Descartar cambios en TODOS los archivos del directorio actual
git restore .
```

## Opción B: El comando clásico

Antiguamente se usaba `checkout`. Todavía es muy común verlo en scripts y documentación antigua.

```Bash
# La sintaxis '--' asegura que Git sepa que hablas de un archivo, no de una rama
git checkout -- archivo.txt
```

---

# 🧹 2. Eliminar archivos nuevos (Untracked)

Los comandos anteriores (`restore` o `checkout`) **no afectan** a los archivos que acabas de crear y nunca has añadido (`untracked files`). Para limpiar estos archivos "basura", usamos `git clean`.

## Paso 1: Simulacro (Dry Run)

Antes de borrar, siempre verifica qué se va a eliminar.

- **-n:** dry run (muestra qué borraría sin hacerlo)

```Bash
git clean -n
```

## Paso 2: Ejecutar limpieza

Si estás seguro, fuerza el borrado.

- **-f:** force (borrar archivos)
- **-d:** directory (borrar también directorios nuevos vacíos)

```Bash
git clean -fd
```

---

# ☸️ Contexto DevOps: ¿Por qué es útil?

En un entorno de **CI/CD** (Integración Continua / Despliegue Continuo), mantener el entorno de trabajo limpio es vital:

- **Build Agents:** Cuando un agente (ej. Jenkins Node, GitLab Runner) reutiliza un espacio de trabajo, a veces quedan archivos temporales o configuraciones generadas de una ejecución anterior fallida.
- **Scripts de Limpieza:** Es común ver un paso `git clean -fdx` al inicio de un pipeline para asegurar que la compilación se realiza sobre un entorno prístino, evitando el error de "funciona en mi máquina (porque tenía un archivo caché viejo)".

---

# ✔️ Resumen rápido

- **Working Directory:** Cambios locales aún no pasados al Staging (`git add` no ejecutado).
- **Recuperar archivo modificado:** Usa `git restore <archivo>`.
- **Eliminar archivos nuevos:** Usa `git clean -fd`.
- **Precaución:** Estos cambios no se pueden recuperar con `git reflog` ni `git reset`.
