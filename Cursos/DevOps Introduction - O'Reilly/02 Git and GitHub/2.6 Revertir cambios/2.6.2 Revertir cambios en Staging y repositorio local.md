# 🔄 Revertir cambios en Staging y Repositorio Local

Una vez que has ejecutado `git add` (pasando archivos al **Staging Area**) o `git commit` (guardándolos en tu **Repositorio Local**), las estrategias para deshacer cambios son diferentes a las del Working Directory. Aquí manipulamos el historial y el estado de preparación.

---

# 📦 1. Revertir cambios en Staging

Si has añadido archivos con `git add` pero te arrepientes y quieres sacarlos del área de preparación (sin borrar tus modificaciones del archivo), usamos el concepto de _Unstage_.

## Opción A: El comando moderno

Al igual que en la nota anterior, `git restore` es la opción semántica correcta desde Git 2.23+.

```Bash
# Sacar un archivo del Staging Area (vuelve a estar solo en Working Directory)
git restore --staged archivo.txt
```

## Opción B: El comando clásico

Antes se utilizaba `reset` apuntando a `HEAD` (el último commit).

```Bash
git reset HEAD archivo.txt
```

---

# 🔙 2. Revertir Commits Locales

Si ya hiciste `git commit`, el cambio está en la historia de tu repositorio local. Para "deshacer" ese commit, usamos `git reset`. Este comando mueve el puntero `HEAD` hacia atrás en el tiempo.

Existen tres modos principales de reset, dependiendo de qué quieras hacer con tu código:

|**Modo**|**Comando**|**¿Qué pasa con el Commit?**|**¿Qué pasa con los cambios?**|
|---|---|---|---|
|**Soft**|`git reset --soft HEAD~1`|Se borra|Se mantienen en **Staging** (listos para commit de nuevo).|
|**Mixed**|`git reset HEAD~1`|Se borra|Se mantienen en **Working Directory** (sin `add`). _Es el default._|
|**Hard**|`git reset --hard HEAD~1`|Se borra|**Se eliminan** permanentemente.|

> [!NOTE]
> HEAD~1 significa _El commit anterior al actual_. Puedes usar HEAD~2 para retroceder dos, etc.

## Ejemplo de uso: Reset Soft

Útil si hiciste un commit pero olvidaste añadir un archivo más.

```Bash
# Deshace el commit, pero deja tus archivos listos para volver a empaquetarlos
git reset --soft HEAD~1
```

---

# 💣 3. El peligro del Hard Reset

El comando `git reset --hard` es muy potente porque iguala tu repositorio, tu staging y tu directorio de trabajo al estado exacto de un commit anterior.

> [!WARNING]
> Pérdida de datos: Cualquier trabajo que no hayas comiteado y cualquier commit que deshagas con --hard se perderá. Úsalo solo si estás seguro de querer descartar todo tu trabajo reciente.

```Bash
# Volver al estado del commit a1b2c3d y borrar todo lo posterior
git reset --hard a1b2c3d
```

---

# 🩹 4. Corregir el último commit (Amend)

A veces no quieres deshacer el commit entero, solo corregir un error tipográfico en el mensaje o añadir un archivo olvidado sin crear un commit nuevo "basura".

```Bash
# 1. Haz tus cambios o git add del archivo olvidado
git add archivo_olvidado.txt

# 2. Ejecuta amend
git commit --amend -m "Nuevo mensaje corregido"
```

Esto **sobrescribe** el último commit (cambia su Hash ID).

---

# ☸️ Contexto DevOps: La Regla de Oro

En un flujo CI/CD y trabajo colaborativo, hay una regla sagrada respecto a `git reset` y `git commit --amend`:

> [!IMPORTANT]
> Nunca reescribas la historia (reset/amend) si ya has hecho PUSH.

**Si tus commits ya están en GitHub/GitLab (Remoto):**

1. Si haces `reset` local y luego intentas subir, Git rechazará el push.
2. Si fuerzas el push (`git push --force`), romperás el historial de todos tus compañeros de equipo.

**Solución DevOps para cambios ya subidos:**

Usa git revert. Este comando crea un nuevo commit que hace lo contrario al commit erróneo, preservando la historia.

```Bash
# Crea un nuevo commit que deshace los cambios del commit indicado
git revert <hash-del-commit-malo>
```

---

# ✔️ Resumen rápido

- **Unstage (`add` por error):** Usa `git restore --staged <archivo>`.
- **Deshacer commit (mantener cambios):** Usa `git reset --soft HEAD~1`.
- **Deshacer commit (borrar todo):** Usa `git reset --hard HEAD~1`.
- **Corregir último commit:** Usa `git commit --amend`.
- **Si ya hiciste Push:** No uses reset, usa `git revert`.
