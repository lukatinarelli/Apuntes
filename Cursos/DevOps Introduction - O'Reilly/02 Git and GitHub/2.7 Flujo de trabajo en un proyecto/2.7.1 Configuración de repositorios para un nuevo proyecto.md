# 🏗️ Configuración de repositorios para un nuevo proyecto

Antes de escribir la primera línea de código funcional, un Ingeniero DevOps debe establecer la "arquitectura del repositorio". Una mala configuración inicial puede llevar a dolores de cabeza con conflictos de merge, ramas desordenadas y pipelines de CI/CD rotos en el futuro.

El objetivo es pasar de un "repositorio vacío" a un "repositorio listo para el equipo".

---

# 🏁 1. Inicialización y Conexión Remota

Existen dos formas comunes de iniciar. La recomendada en entornos corporativos es crear primero el repositorio en remoto (GitHub/GitLab) para configurar permisos, y luego clonarlo.

## Opción A: Crear en Remoto y Clonar (Recomendado)

1. Crear repo en GitHub (marcar opción "Add README").
2. Clonar en la máquina local.

```Bash
git clone https://github.com/usuario/mi-proyecto.git
cd mi-proyecto
```

## Opción B: Iniciar Local y Subir

Si ya tienes código localmente:

```Bash
git init
git add .
git commit -m "Initial commit"

# Vincular con el remoto (previamente creado vacío en GitHub)
git remote add origin https://github.com/usuario/mi-proyecto.git
git push -u origin main
```

---

# 🌿 2. Establecer la Estrategia de Ramas Base

En un flujo DevOps profesional, rara vez trabajamos solo en `main`. Necesitamos reflejar los entornos de despliegue (Development, Testing/UAT, Production) en nuestras ramas.

Al configurar el proyecto, debemos crear estas ramas base inmediatamente.

## Ramas Estándar

- **`main` / `master`:** Código estable, representa **Producción**.
- **`dev` / `develop`:** Rama de integración. Aquí se unen las funcionalidades nuevas. Representa el entorno de **Desarrollo**.
- **`uat` / `release`:** (Opcional según el proyecto) Para pruebas de aceptación de usuario.

## Configuración inicial en terminal

Estando en `main` (limpio), creamos la rama de desarrollo:

```Bash
# Crear rama dev y cambiarse a ella
git checkout -b dev

# Subir la rama al repositorio remoto
git push -u origin dev
```

> [!NOTE]
> A partir de este momento, el equipo de desarrollo debería clonar el repo y empezar a trabajar basándose en dev, no en main.

# 📜 3. Archivos de Gobernanza

Un proyecto profesional necesita tres archivos clave en la raíz desde el día 1:

1. **`.gitignore`:** [(Visto en la sección 2.6.3)](../2.6%20Revertir%20cambios/2.6.3%20Archivo%20.gitignore.md) Para evitar subir basura.
2. **`README.md`:** Documentación básica. Debe explicar cómo instalar y ejecutar el proyecto localmente.
3. **`LICENSE`:** Define cómo se puede usar el código.

```
# Ejemplo de estructura de directorio inicial
/mi-proyecto
├── .git/
├── .gitignore
├── README.md
└── src/
```

---

# 🛡️ 4. Protección de Ramas (Branch Protection Rules)

Como DevOps, debes configurar GitHub para evitar errores humanos. Esto no se hace por comando, sino en la UI de GitHub (`Settings` -> `Branches` -> `Add rule`).

Reglas recomendadas para empezar:

1. **Branch name pattern:** `main` y `dev`.
2. **Require pull request reviews:** Nadie puede hacer push directo; todo cambio debe pasar por una Pull Request (PR) y ser aprobado por al menos 1 persona.
3. **Require status checks to pass:** (Para el futuro) El código no se puede fusionar si el pipeline de CI falla (tests, linter, build).

---

# ☸️ Contexto DevOps: Preparando el CI/CD

Esta configuración inicial es el cimiento del pipeline:

- Al tener una rama `dev`, podremos configurar un **Pipeline de Integración** que se dispare automáticamente con cada cambio ahí.
- Al proteger `main`, aseguramos que **Producción** solo reciba código que ha pasado por `dev` y ha sido aprobado.

---

# ✔️ Resumen rápido

1. Iniciar repositorio (preferiblemente clonando desde remoto).
2. Añadir archivos base (`README.md`, `.gitignore`).
3. Crear y subir la rama `dev` (`git checkout -b dev`).
4. Configurar **reglas de protección** en GitHub para impedir commits directos a `main`.
