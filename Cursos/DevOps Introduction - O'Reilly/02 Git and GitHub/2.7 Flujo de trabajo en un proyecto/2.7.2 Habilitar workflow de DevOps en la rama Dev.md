# 🚀 Habilitar workflow de DevOps en la rama Dev

La rama `dev` (o `develop`) actúa como la **columna vertebral de la integración**. En un flujo de trabajo DevOps, esta rama representa el código _bleeding edge_: contiene las últimas funcionalidades de todo el equipo, pero **no garantiza estabilidad total**.

"Habilitar el workflow" significa adoptar la disciplina de las **Feature Branches** (Ramas de funcionalidad). Ningún desarrollador debería hacer commit directamente en `dev`; en su lugar, deben crear una rama lateral y luego fusionarla.

---

# 🌿 1. El ciclo de vida: Feature Branches

Cada tarea nueva (una nueva pantalla, un botón, una corrección de base de datos) nace en su propia rama aislada. Esto permite que varios desarrolladores trabajen en paralelo sin romperse el código mutuamente.

## Naming Convention (Convención de Nombres)

Es vital tener nombres estandarizados para identificar el propósito de la rama:

- `feature/nombre-funcionalidad` (ej: `feature/login-page`)
- `bugfix/nombre-error` (ej: `bugfix/header-css`)
- `hotfix/error-critico` (ej: `hotfix/security-patch` - _estos suelen ir directo a main_)

## Paso a paso: Crear una feature branch

Supongamos que vas a crear un formulario de contacto.

```Bash
# 1. Actualizar tu repositorio local con lo último del remoto
git checkout dev
git pull origin dev

# 2. Crear la rama basada en dev
git checkout -b feature/contact-form

# 3. Trabajar... (editar archivos)
echo "Formulario v1" > contact.html

# 4. Guardar cambios
git add .
git commit -m "feat: Add basic contact form structure"
```

---

# ⬆️ 2. Publicar la rama (Push)

Una vez terminada la tarea localmente, la rama debe subirse al repositorio remoto (GitHub/GitLab). Esto **NO** integra el código todavía, solo lo hace disponible para revisión.

```Bash
# La primera vez que subes una rama nueva
git push -u origin feature/contact-form
```

---

# 🔀 3. La Pull Request (PR) hacia Dev

Aquí es donde se "habilita" la magia de DevOps. En lugar de hacer un `git merge` manual en tu terminal, vas a la plataforma (GitHub) y abres una **Pull Request (PR)**.

- **Origen:** `feature/contact-form`
- **Destino:** `dev` (¡Importante! No apuntar a `main` todavía)

> [!IMPORTANT]
> **El disparador de CI (Integración Continua):**
> 
> En un entorno DevOps configurado, el acto de abrir una PR o fusionar código en la rama dev es el evento disparador (trigger).
> 
> 1. El desarrollador hace Merge a `dev`.
>     
> 2. GitHub/GitLab detecta el cambio.
>     
> 3. Se dispara automáticamente un pipeline (Jenkins, GitHub Actions).
>     
> 4. El pipeline ejecuta Tests Unitarios y Linters.
>     

---

# 🔄 4. Actualización constante (Evitar conflictos)

Mientras trabajas en tu `feature/contact-form`, tus compañeros pueden haber fusionado sus propios cambios en `dev`. Tu rama se está quedando "vieja".

Para evitar un infierno de conflictos al final, debes traer los cambios de `dev` a tu rama frecuentemente:

```Bash
# Estando en tu rama feature/contact-form
git pull origin dev
```

Esto fusiona lo nuevo de `dev` en tu rama, permitiéndote resolver conflictos localmente antes de subir tu código.

---

# ✔️ Resumen rápido

1. **Nunca** trabajes directo en `dev` o `main`.
2. Crea una rama `feature/mi-tarea` desde `dev`.
3. Sube la rama con `git push`.
4. Crea una **Pull Request** apuntando a `dev`.
5. Este flujo permite que el sistema de **CI (Integración Continua)** valide el código automáticamente cada vez que alguien integra algo nuevo en `dev`.
