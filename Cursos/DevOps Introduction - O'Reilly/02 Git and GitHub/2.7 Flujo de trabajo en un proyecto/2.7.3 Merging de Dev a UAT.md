# 🧪 Merging de Dev a UAT

Una vez que las funcionalidades han sido integradas en la rama `dev` y los desarrolladores creen que "todo funciona", no podemos pasar directo a Producción. Necesitamos un **entorno de validación**. Aquí entra en juego la rama `uat` (a veces llamada `release` o `staging`).

## ¿Qué es UAT?

**UAT (User Acceptance Testing)** es la etapa donde el usuario final (o un representante del negocio/QA) prueba el software en un entorno controlado que simula la realidad.

- **Objetivo:** Responder a la pregunta: _"¿Es esto lo que pidió el cliente?"_.
- **Regla de Oro:** En esta rama **NO se programa**. Solo se reciben fusiones desde `dev`.

---

# 📦 1. El concepto de "Congelar Código" (Code Freeze)

La rama `dev` es muy volátil (cambia varias veces al día). La rama `uat` debe ser estable.

Cuando decidimos pasar código de dev a uat, estamos haciendo una Release Candidate (Candidata a lanzamiento).

En este punto, decimos: _"Vamos a dejar de añadir cosas nuevas y vamos a probar lo que tenemos"_.

---

# 🔀 2. El proceso de Merge (Promoción)

Técnicamente, estamos promocionando el código. Esto se suele hacer mediante una Pull Request para dejar registro, pero a nivel de comandos de Git, el flujo es traer los cambios de desarrollo hacia UAT.

## Opción A: Vía Pull Request

En GitHub/GitLab:

1. Crear PR.
2. **Base:** `uat` (destino).
3. **Compare:** `dev` (origen).
4. Título: "Release v1.2.0 a UAT".

## Opción B: Vía Terminal

Si eres el responsable de la release y lo haces localmente:

```Bash
# 1. Moverse a la rama UAT
git checkout uat

# 2. Asegurarse de tener la última versión de UAT (por si hubo parches)
git pull origin uat

# 3. Fusionar lo que hay en DEV hacia UAT
git merge dev

# 4. Subir los cambios al remoto
git push origin uat
```

---

# 🐛 3. ¿Qué pasa si encuentran un error en UAT?

Si el cliente prueba la aplicación en UAT y encuentra un bug, **NO** se arregla en `dev` (porque `dev` ya ha avanzado con cosas nuevas) ni se programa directo en `uat`.

Se crea una rama de **Hotfix** (o Bugfix de Release):

1. Se crea una rama temporal desde `uat`.
2. Se arregla el error.
3. Se fusiona de vuelta a `uat`.
4. **IMPORTANTE:** Ese arreglo también debe fusionarse hacia `dev` para que los desarrolladores no reintroduzcan el error en el futuro.

---

# ☸️ Contexto DevOps: Despliegue Automático

En un pipeline CI/CD bien configurado, el acto de hacer el **merge a la rama UAT** dispara un proceso de despliegue diferente al de desarrollo:

1. **Trigger:** Commit detectado en rama `uat`.
2. **Build:** Se compila la aplicación (optimizada para producción).
3. **Deploy:** Se sube el código a un servidor de "Staging" (ej. `uat.miempresa.com`).
4. **Notificación:** Se envía un email/Slack al equipo de QA: _"La versión X está lista para pruebas"_.

---

# ✔️ Resumen rápido

- **UAT:** Entorno de pruebas para el cliente/negocio.
- **Flujo:** El código viaja `dev` ➡️ `uat`.
- **Estabilidad:** `dev` es rápido y sucio; `uat` es lento y estable.
- **Acción:** Al fusionar en esta rama, se suele desplegar automáticamente en un servidor de pruebas idéntico al real.
