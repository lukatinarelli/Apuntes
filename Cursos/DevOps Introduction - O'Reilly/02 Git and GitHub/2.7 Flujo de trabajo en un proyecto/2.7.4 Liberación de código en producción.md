# 🚀 Liberación de código en producción

La rama `main` (o `master`) es sagrada. Representa la **"Golden Copy"** (Copia Dorada) del software. Todo lo que existe en esta rama debe ser estable, probado y funcional.

La "liberación" (Release) es el acto de fusionar el código validado desde `uat` hacia `main` y, crucialmente, ponerle una **etiqueta (Tag)** de versión.

---

# 🔀 1. El Merge Final

El flujo es estricto: el código nunca salta de `dev` a `main`. Debe haber pasado por el filtro de `uat`.

## Procedimiento

Desde la terminal o mediante una Pull Request "UAT to Main":

```Bash
# 1. Cambiar a la rama principal
git checkout main

# 2. Asegurarse de que main está actualizada (por si hubo hotfixes previos)
git pull origin main

# 3. Fusionar la rama UAT (que ya fue aprobada por el cliente)
git merge uat

# 4. Subir los cambios
git push origin main
```

> [!WARNING]
> En muchas empresas, la rama main está bloqueada para push directos. Este proceso suele hacerse exclusivamente vía Pull Request aprobada por un líder técnico o DevOps Lead.

# 🏷️ 2. Tagging (Etiquetado de versiones)

Git tiene una funcionalidad específica para marcar puntos importantes en la historia: los Tags.

Mientras que las ramas (main, dev) son punteros que se mueven con cada commit, un Tag es inmutable. Se queda fijo en un commit específico para siempre.

## ¿Por qué usamos Tags?

Para poder decir: _"El código en este punto exacto es la versión 1.0.0"_. Si hay un error en el futuro, podemos volver exactamente a este punto.

## Comandos de Tagging

```Bash
# Crear un tag anotado (recomendado para releases)
# -a: anotado
# -m: mensaje de la versión
git tag -a v1.0.0 -m "Versión 1.0.0 - Lanzamiento inicial"

# Ver los tags creados
git tag

# IMPORTANTE: Los tags no se suben con un 'git push' normal.
# Debes subirlos explícitamente:
git push origin v1.0.0
# O para subir todos los tags nuevos:
git push --tags
```

---

# 🔢 3. Versionado Semántico (SemVer)

En DevOps, no inventamos números al azar. Seguimos el estándar **Semantic Versioning** (`MAJOR.MINOR.PATCH`):

- **MAJOR (v1.0.0):** Cambios incompatibles con la versión anterior (Breaking changes).
- **MINOR (v1.1.0):** Nueva funcionalidad compatible hacia atrás (Features).
- **PATCH (v1.1.1):** Corrección de errores compatibles hacia atrás (Bugfixes).

# ☸️ Contexto DevOps: GitHub Releases

Cuando subes un Tag a GitHub/GitLab, la plataforma suele reconocerlo y te permite crear una **"Release"** en la interfaz gráfica.

El Pipeline de Producción:

En un sistema CI/CD maduro, el evento disparador para desplegar en el servidor de Producción suele ser la creación de un Tag.

1. DevOps hace: `git push origin v1.0.0`
2. GitLab CI / GitHub Actions detecta el tag que empieza por `v*`.
3. El pipeline compila el código.
4. **Despliegue:** El artefacto se sube automáticamente a los servidores de Producción (AWS, Azure, Kubernetes, etc.).

---

# ✔️ Resumen del Flujo Completo

1. **Dev:** Programadores crean código (`feature branch` ➡️ `dev`).
2. **UAT:** Se congela el código para pruebas (`dev` ➡️ `uat`).
3. **Prod:** Se aprueba y se libera (`uat` ➡️ `main`).
4. **Tag:** Se "firma" la versión (`git tag v1.0.0`).
