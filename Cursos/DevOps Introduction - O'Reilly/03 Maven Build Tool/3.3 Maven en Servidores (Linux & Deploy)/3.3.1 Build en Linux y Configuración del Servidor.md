# 🐧 Build en Linux y Configuración del Servidor

Hasta ahora hemos trabajado en un entorno de desarrollo (IDE/Eclipse). Ahora nos ponemos el sombrero de DevOps: vamos a configurar un **Servidor de Build** (Linux) que será el encargado de compilar el código de manera oficial y automatizada.

El flujo será: `GitHub` ➡️ `Servidor Linux` ➡️ `Maven Build` ➡️ `Artefacto (.jar/.war)`.

-----

# 🛠️ 1. Preparación del Servidor (Provisioning)

Asumimos que lanzamos una instancia EC2 (AWS) con Amazon Linux 2 o cualquier distro basada en RHEL/CentOS.

## A. Prerrequisitos

Un servidor de Build necesita dos cosas básicas: **Java** (para correr Maven) y **Git** (para bajar el código).

```bash
# 1. Instalar Java (OpenJDK)
sudo yum install java-1.8.0-openjdk-devel -y

# 2. Verificar Java
java -version

# 3. Instalar Git
sudo yum install git -y
```

## B. Instalación Manual de Maven

A diferencia de `apt` o `yum`, a menudo queremos una versión específica de Maven, así que la instalamos manualmente en `/opt`.

```bash
# 1. Descargar el binario (tar.gz) desde la web oficial
wget https://downloads.apache.org/maven/maven-3/3.8.6/binaries/apache-maven-3.8.6-bin.tar.gz

# 2. Descomprimir en /opt
sudo tar -xvzf apache-maven-3.8.6-bin.tar.gz -C /opt

# 3. Renombrar para facilitar el acceso (opcional)
sudo mv /opt/apache-maven-3.8.6 /opt/maven
```

## C. Variables de Entorno (El paso clave)

Para que el comando `mvn` funcione en cualquier carpeta, debemos añadirlo al `PATH`.

Editar el archivo de perfil (`vi ~/.bash_profile` o `/etc/profile`):

```bash
export M2_HOME=/opt/maven
export PATH=$PATH:$M2_HOME/bin
```

Recargar configuración: `source ~/.bash_profile`.
Verificar: `mvn -version`.

# 🏗️ 2. El Proceso de Build en Servidor

Ahora que el servidor tiene Maven, simulamos lo que haría Jenkins.

1.  **Clonar el Repo:**

    ```bash
    git clone https://github.com/usuario/mi-web-app.git
    cd mi-web-app
    ```

2.  **Ejecutar el Build:**
    Al igual que en local, lanzamos los goals.

      * **`mvn compile`**: Solo compila. Verás que se crea la carpeta `target/`.
      * **`mvn package`**: Crea el `.war` o `.jar`.
      * **`mvn install`**: Guarda el artefacto en la caché local del servidor.

> [!NOTE]
> **La primera ejecución es lenta:** El servidor tiene su carpeta `.m2` vacía. La primera vez que ejecutes `mvn package`, descargará "medio internet". Las siguientes veces volará.

-----

# ⚙️ 3. El archivo `settings.xml`

Existe un archivo de configuración **global** para Maven llamado `settings.xml`.

  * **Ubicación:** Generalmente en `~/.m2/settings.xml` o en `/opt/maven/conf/settings.xml`.

## ¿Para qué sirve?

Mientras que el `pom.xml` configura **un proyecto**, el `settings.xml` configura **el entorno de Maven**.

Se usa principalmente para:

1.  **Credenciales:** Guardar usuarios y contraseñas de servidores remotos (Nexus, SonarQube, Tomcat) para no ponerlos en el código.
2.  **Proxies:** Si el servidor corporativo necesita salir a internet por un proxy.
3.  **Mirrors:** Para obligar a Maven a descargar librerías de un espejo interno en lugar del central público.

# ☸️ Contexto DevOps: Automatización

Este proceso manual que acabamos de hacer (`ssh` -\> `git clone` -\> `mvn package`) es exactamente lo que automatizaremos con **Jenkins** en el siguiente módulo.

Jenkins será quien se conecte a este servidor (o use uno propio), clone el repo y ejecute `mvn clean package` sin intervención humana.
