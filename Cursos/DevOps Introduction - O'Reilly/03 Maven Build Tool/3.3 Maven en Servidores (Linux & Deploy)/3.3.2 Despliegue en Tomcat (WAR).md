# 🚀 3.3.2 Despliegue en Tomcat (WAR)

Generar un archivo `.war` (Web Archive) no sirve de nada si se queda en tu disco duro. Necesitamos desplegarlo en un **Servidor de Aplicaciones** para que los usuarios puedan acceder vía web.

En este laboratorio conectaremos dos servidores:

1. **Maven Build Server:** Donde compilamos el código (Source).
2. **Tomcat Server:** Donde se ejecuta la aplicación (Destination).

---

# 🔐 1. Preparar el Destino (Tomcat)

Tomcat por defecto viene "cerrado". Para que Maven pueda inyectarle un archivo `.war` remotamente, necesitamos crear un usuario con permisos de gestor.

**Archivo:** `/opt/apache-tomcat/conf/tomcat-users.xml`

Debes añadir un usuario con los roles `manager-gui` y `manager-script`.

```XML
<tomcat-users>
    <role rolename="manager-gui"/>
    <role rolename="manager-script"/>
    
    <user username="admin" password="admin_password" roles="manager-gui,manager-script"/>
</tomcat-users>
```

> [!NOTE]
> Después de editar este archivo, es obligatorio reiniciar Tomcat (./shutdown.sh y ./startup.sh).

---

# 🔑 2. Configurar Credenciales en Maven (Source)

Como buena práctica de seguridad, **nunca** ponemos contraseñas en el código del proyecto (`pom.xml`). Las credenciales se guardan en el archivo de configuración global del servidor de Maven.

**Archivo:** `~/.m2/settings.xml`

```XML
<settings>
  <servers>
    <server>
      <id>TomcatServer</id> <username>admin</username>
      <password>admin_password</password>
    </server>
  </servers>
</settings>
```

---

# 🔌 3. Configurar el Plugin en `pom.xml`

Ahora le decimos a nuestro proyecto: _"Usa el plugin de Tomcat para enviar el archivo, y coge las contraseñas del servidor llamado 'TomcatServer'"_.

**Archivo:** `pom.xml` (Sección `<plugins>`)

```XML
<plugin>
    <groupId>org.apache.tomcat.maven</groupId>
    <artifactId>tomcat7-maven-plugin</artifactId>
    <version>2.2</version>
    <configuration>
        <url>http://<IP-DEL-TOMCAT>:8080/manager/text</url>
        
        <server>TomcatServer</server>
        
        <path>/mi-app</path>
    </configuration>
</plugin>
```

---

# 🎯 4. Ejecutar el Despliegue

Ya no usamos el comando estándar `mvn deploy` (que subiría a Nexus), sino que invocamos directamente al plugin de Tomcat.

## Primer Despliegue

```Bash
mvn tomcat7:deploy
```

Si todo va bien, verás un `BUILD SUCCESS` y podrás entrar en tu navegador: `http://<IP-DEL-TOMCAT>:8080/mi-app`.

## Actualizaciones (Redeploy)

Si cambias el código (ej. modificas `index.jsp`) e intentas hacer `deploy` de nuevo, fallará porque la aplicación ya existe.

**Solución 1 (Correcta):** Usar el comando de redespiegue.

```Bash
mvn tomcat7:redeploy
```

**Solución 2 (Manual/Video):** Entrar al servidor Tomcat, borrar la carpeta de la app en `webapps/` y volver a lanzar el deploy. (No recomendado en producción).

---

# ☸️ Contexto DevOps

Lo que acabamos de hacer es un **Deployment Automatizado** básico.

- **Antes:** Copiabas el archivo `.war` por SCP/FTP y reiniciabas el servidor a mano.
- **Ahora:** Un comando (`mvn tomcat7:redeploy`) gestiona la transferencia y el reinicio en caliente.

Esto es la base para que **Jenkins** pueda hacer deployments con un solo clic en el siguiente módulo.
