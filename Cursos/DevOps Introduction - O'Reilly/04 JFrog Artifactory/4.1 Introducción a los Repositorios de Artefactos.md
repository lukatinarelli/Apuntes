# 📦 Introducción a los Repositorios de Artefactos

Antes de instalar herramientas, debemos entender el problema que resuelven. En el ciclo de vida del software, existe una diferencia crítica entre el **código fuente** y el **entregable final**.

# 🧱 1. ¿Qué es un Artefacto (Artifact)?

Los desarrolladores escriben **Código Fuente** (Source Code) en lenguajes legibles por humanos (Java, C#, Python). Sin embargo, las máquinas no ejecutan código fuente directamente; necesitan binarios.

El proceso de **Compilación/Build** transforma el código fuente en un **Artefacto**.

- **Definición:** Un artefacto es el resultado binario e inmutable del proceso de construcción de software.
- **Ejemplos:**
    - **Java:** `.jar`, `.war`, `.ear`
    - **.NET:** `.exe`, `.dll`
    - **Contenedores:** Imágenes de Docker

> [!NOTE]
> **Analogía:** El código fuente es la receta de cocina. El artefacto es el pastel terminado. No puedes "comer" la receta, necesitas cocinarla (compilarla) primero.

---

# 🚫 2. El problema: ¿Por qué no usar Git?

Una pregunta común de principiante es: _"Si ya tengo Git y GitHub, ¿por qué no subo el archivo .jar compilado ahí?"_.

Git es un **Sistema de Control de Versiones (VCS)** diseñado para **texto**.

1. **Ineficiencia:** Git guarda los cambios (diferencias) línea por línea. Los binarios no tienen líneas; si cambias un byte en un archivo de 100MB, Git tiene que guardar una copia nueva completa de 100MB. Esto hace que el repositorio sea gigante y lento.
2. **Seguridad y Propiedad Intelectual:** A los clientes se les entrega el producto (el binario), no la fórmula secreta (el código fuente). Necesitamos un lugar para almacenar lo que entregamos al cliente sin darle acceso a nuestro Git.
3. **Inmutabilidad:** Un artefacto, una vez creado (versión 1.0), no debería cambiar jamás. Git está diseñado para cambiar constantemente.

> [!WARNING]
> **Regla de Oro:** Jamás subas carpetas bin/, obj/, target/ o archivos .jar/.exe al repositorio de Git. Usa .gitignore para bloquearlos.

---

# 🏦 3. ¿Qué es un Repositorio de Artefactos?

Si no podemos usar Git, necesitamos un almacén especializado para binarios. Aquí entran herramientas como **JFrog Artifactory** o **Sonatype Nexus**.

Un Gestor de Repositorios de Artefactos cumple una doble función vital en DevOps:

## A. Almacén de Salida (Target)

Actúa como destino para nuestros builds.

- El servidor CI (Jenkins/Maven) compila el código.
- Sube el resultado (`mi-app-1.0.jar`) a Artifactory.
- Esto nos permite tener un histórico de versiones ("Esta es la v1.0 que funcionaba, esta es la v1.1 que falló").

## B. Proxy de Dependencias (Source/Cache)

Actúa como intermediario entre tu empresa e Internet.

- **Sin Artifactory:** Cada vez que haces `mvn install`, Maven va a "Maven Central" (Internet) y descarga las librerías. Si tienes 100 desarrolladores, son 100 descargas idénticas.
- **Con Artifactory:**
    1. El desarrollador pide `junit`.
    2. Artifactory mira si lo tiene.
    3. Si no, lo baja de Internet **una vez** y lo guarda.
    4. El resto de desarrolladores lo descargan de Artifactory (Red Local/Privada).

---

# 🛡️ 4. Ventajas en el flujo DevOps

1. **Velocidad:** Las descargas desde un servidor local (Artifactory) son mucho más rápidas que ir a Internet.
2. **Seguridad:** Puedes bloquear librerías externas maliciosas o vulnerables antes de que entren en tu red.
3. **Consistencia:** Garantizas que todos los desarrolladores usen exactamente la misma versión de las librerías.
4. **Alta Disponibilidad:** Si Maven Central se cae o tu empresa pierde internet, puedes seguir trabajando porque tienes una copia (caché) de todo lo necesario.
